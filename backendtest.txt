Phase 3 — Database integrity and abuse prevention
This phase covers the Prisma schema and operations across the application.

We'll check:
- [ ] Duplicate follows.
- [ ] Duplicate saved posts.
- [ ] Duplicate reports.
- [ ] Duplicate likes and blocks (already protected by unique constraints).
- [ ] Concurrent requests and race conditions.
- [ ] Appropriate database indexes and constraints.
- [ ] Whether deleting users or posts leaves unwanted related records.
- [ ] Whether block relationships are respected consistently.
We'll only create migrations where they're genuinely necessary.
Phase 4 — Authentication and security boundary checks
We'll verify:
- [ ] All private backend operations reject unauthenticated requests.
- [ ] Client-supplied IDs cannot impersonate another user.
- [ ] Server actions validate their arguments, even when called directly.
- [ ] API routes don't trust frontend restrictions.
- [ ] Sensitive operations handle invalid or manipulated inputs safely.
- [ ] Clerk webhooks remain protected by signature verification.
- [ ] Socket.IO notifications cannot be sent to unauthorized rooms.
- [ ] Errors don't expose secrets, internal credentials or sensitive database details.
Phase 5 — Final security testing
We'll test the important attack scenarios rather than relying only on code inspection.
Test	Expected result
Signed-out user calls a private action	Rejected
User edits another user's profile	Rejected
User deletes another user's post	Rejected
User accesses another person's notifications	Rejected
User manipulates a notification ID	No unauthorized update
User accesses blocked user's restricted content	Denied
User submits invalid post data	Rejected
User submits duplicate follow/save/report requests	Handled safely
User requests unauthorized uploads	Rejected or restricted

When will we consider the audit finished?
We'll be finished when:
1. Every listed server action and API route has been reviewed.
2. Every identified security issue has either been fixed or explicitly documented as an accepted limitation.
3. Necessary database migrations have been applied and verified.
4. The critical authorization tests pass.
5. Existing features still work: authentication, posts, comments, likes, follows, reposts, notifications, blocking, reporting, uploads and profile editing.
Our working rule: One file or closely related group of operations at a time. Inspect, identify issues, agree on the fix, implement, run TypeScript checks, and test. Then mark that item complete.
